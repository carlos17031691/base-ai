# Global rules for AI agents

> Single source of truth (ADR-0001). Exported to AGENTS.md, CLAUDE.md, .cursor/rules and Copilot. Services may extend via `src/<name>/.ai/rules.md` (local wins). Never hand-edit files marked `generated by base-ai`; edit `.ai/` and run `base-ai ai sync`.

## 1. Mission & adaptive guidance
- Help **any developer (beginner to architect)** design, build, integrate, test, secure, deploy and operate production software.
- **Guide proactively:** from raw ideas, walk through discovery, service breakdown, Epics/User Stories (`discovery`), stack choice, branch setup and incremental delivery (`sdlc`).
- **Explain trade-offs:** state *why* a pattern, store, model or control is chosen before writing code. Ask concise questions whenever requirements are ambiguous.

## 2. Isolation boundaries
- The root repo is an **umbrella template** with no application code.
- Each service in `src/<name>/` is an **independent Git repository** registered in `services.yaml` with its own remote (`repo`), stack, data, infra and CI/CD.
- Never import across services or from the root via filesystem paths; communicate **only through versioned contracts** (APIs, events, schemas).
- Scope every change to a single repository (root or one `src/<name>`).

## 3. Git workflow, ticket traceability & PR policy (root & `src/<name>`)
Enforced by `.githooks/`:
1. **Mandatory ticket & plan approval:** every change requires an approved plan (`discovery` / `sdlc` Gate 1) and a Story/Epic/Task ID (Jira, ClickUp, Trello, GitHub Issues, etc., e.g. `PROJ-123`, `CU-86a1b2`, `#45`). Ask for it if missing and never write code before Gate 1 approval.
2. **Working branch from `development`:** never commit on `main`, `master` or `development`. Create a ticket branch from `development` first (e.g. `git checkout -b feat/PROJ-123-short-slug development`).
3. **Commit message:** reference the ticket ID in every commit (`feat(PROJ-123): ...`).
4. **Pull Request to `development`, dual quality gates & mandatory human approval:** never push directly to `main`, `master` or `development`; push the working branch, open a PR targeting **`development`** (`staging`), publish the `review` + `security` audit report on the PR, and obtain mandatory **human approval**. Promote `development` → `main` via release PR for `production`.

## 4. SDLC & clean code
- **Lifecycle (`sdlc`):** Understand & trace → Branch & design (`adr` / `rfc`) → Implement & test (`testing`) → Review (`review` + `security`) → Operate (`observability`, `infrastructure`, `docs`, `runbook`, postmortem).
- **Quality gates & PR review policy (`review`):** enforce a dual review gate on every PR: deterministic SAST & test coverage (SonarQube/SonarCloud >= 80% coverage, zero vulnerabilities via `sonar-project.properties`) and cognitive review (CodeRabbit via `.coderabbit.yaml` validating ticket traceability, isolation boundaries, clean code and security). All findings must be triaged by severity before **human approval**:
  - **High & Medium (Blocking):** MUST be resolved and corrected in code before human approval. Never merge with unresolved High or Medium issues.
  - **Low (Non-blocking / Tech Debt):** May be approved without blocking the PR, provided they are explicitly registered as technical debt (creating a project Issue/Ticket).
- **Clean code:** apply **SOLID**, **KISS**, **YAGNI** and pragmatic **DRY**. Use intention-revealing names, small cohesive functions, guard clauses, strict types and immutability.
- **Errors & comments:** fail fast on bugs; return typed errors on domain/I/O failures; never swallow errors. Comment *why*, not *what*; preserve unrelated comments and match the service's style/linter.

## 5. Architecture, AI, data & operations
- **Boundaries (`architecture`):** isolate domain logic from transport and infrastructure (Dependency Inversion).
- **Integrations & AI gateways (`integrations`):** wrap external APIs, webhooks and LLM gateways (e.g. OpenRouter, LiteLLM) behind domain ports with timeouts, backoff+jitter retries, model fallbacks, `Idempotency-Key` and webhook HMAC verification.
- **AI usage & token FinOps (`ai-ops`):** tier models by complexity, structure prompts for prefix caching (static first), cap `max_tokens`, and track input/cached/output tokens, latency and USD cost. Conserve coding tokens via `base-ai context search` and `base-ai ai stats`.
- **Agents & workflows (`agents`, `workflows`):** keep agent/MCP tools atomic, least-privilege and idempotent with Human-in-the-Loop for sensitive actions and hard step/cost caps. Isolate workflow engines (e.g. n8n, Temporal) in their own `src/<name>` repo, version workflows in Git via PRs and keep secrets out of workflow JSON.
- **Memory & RAG (`memory`, `rag`):** store cross-session learnings in `.ai/memory.md` (`base-ai memory add/list`, zero secrets/PII). In apps, isolate short/long-term memory and RAG chunks by `tenant_id`/`user_id` before retrieval, use hybrid search, cite sources and defend against indirect prompt injection.
- **Data, observability & cloud infra (`database`, `observability`, `infrastructure`):** per-service DB ownership, expand-and-contract migrations, parameterized queries; JSON logs with `trace_id`, RED/USE metrics, `/healthz`+`/readyz` and Monitoring-as-Code alarms (compute, DB, DLQ, cloud budgets); 12-Factor config, non-root containers, keyless OIDC cloud auth, PR `plan` → `apply` GitOps and automated rollback.

## 6. Security by design (`security`)
- **Zero secrets/PII** in code, tests, logs, memory, prompts or docs; load from env/secret manager.
- **Validate all untrusted input** (HTTP, webhooks, CLI, files, queues, LLM/tool outputs) at boundaries; enforce least-privilege authn/authz and pin vetted dependencies.
